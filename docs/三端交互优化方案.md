# 三端交互优化方案

> **实施状态**：P0、P1、P2 已完成。P0 含通知表、发布通知、未读接口、小程序角标与下拉刷新、管理端发布确认与徽标轮询；P1 含成绩/关闭/加入审核通知、截止前 24 小时定时提醒、员工停用校验、考试排序与 computed_state、消息中心页、已发布考试追加指派、答题页保存状态；P2 含微信订阅消息（可配置、失败降级）、管理端通知送达统计、员工截止提醒偏好。
>
> 范围：管理后台（admin-web）、员工端小程序（frontend）、后端（backend）
> 目标：让管理员的动作（发布考试、审核加入、发布知识卡、关闭考试）能主动触达员工；同时收敛三端的数据刷新、状态一致性与异常路径。

---

## 一、现状与问题

### 1.1 员工端：只能靠"进页面"或"切页面"刷新

| 位置 | 现状 | 问题 |
|---|---|---|
| `pages/index/index.tsx` | `useDidShow` 时调 `listEmployeeExams()` 计算待办数 | 只为了一个数字拉全量考试列表；停在首页不切页永远看不到新考试 |
| `pages/employee-exams/index.tsx` | `useDidShow` 拉列表 | 同上，无下拉刷新、无新消息提示 |
| `pages/employee-wrong`、`profile` | `useDidShow` | 一致但无感知 |
| `app.config.ts` | 未使用 tabBar 角标 | 新考试只能进页面后才发现 |
| 页面 | 未配置 `enablePullDownRefresh` | 用户没有手动刷新入口 |

**结论**：管理员发布考试后，员工必须切一次页面（或杀进程重进）才能看到。这是当前最明显的体验断点。

### 1.2 设置页的四个通知开关是"空开关"

`tenant_settings` 已有 `notify_assigned / notify_result / notify_deadline / notify_cards`，设置页也有对应表单项，但后端没有任何实现。用户打开开关不会发生任何事——这是必须补齐的承诺。

### 1.3 管理端：待办徽标只在路由切换时更新

`AdminLayout.tsx:155` 的 `useEffect` 依赖 `location.pathname`，只在换页时拉一次 `getDashboard()`。停留在工作台时，新加入申请、新题目、新知识卡都不会自动冒红点。

发布考试成功后没有"已通知多少人"的反馈，管理员无法判断员工是否收到。

### 1.4 员工身份与考试状态的一致性缺口

- `get_employee_context`（`backend/app/core/auth.py:130`）只校验 JWT 载荷，不查员工当前状态。员工被停用后，旧 token 仍可访问 `/employee/exams` 等接口，直到 token 过期。
- 考试发布后不能再调整指派（`assign_exam` 仅草稿可用），新入职员工看不到已发布考试，也没有补救入口。
- 考试列表 SQL 按 `assigned_at DESC` 排序，但页面文案写着"按截止时间优先完成"，排序与文案不一致。
- 截止时间已过、从未开始的考试，状态显示"已结束"，与"未参加"语义混淆。

### 1.5 其他

- 答题页自动保存失败时只有一次 toast，网络恢复后不会补传。
- 加入申请被通过/驳回后，员工端只有在重新进入 `employee-login` 时才会发现。
- 管理端看板数据不会随考试发布、成绩提交自动更新。

## 二、总体设计

### 2.1 两条通道，主次分明

```
                      ┌─────────────────────────────┐
  管理员动作 ────────▶ │  通知写入层 notifications    │
  (发布/关闭/审核/发布卡) │  (事务提交后异步批量写入)     │
                      └──────────────┬──────────────┘
                                     │
              ┌──────────────────────┴──────────────────────┐
              ▼                                             ▼
   站内消息通道（默认，始终可用）                微信订阅消息（可选增强）
   - 未读计数接口                                - 用户授权后发一次
   - tabBar 角标                                 - 一次性订阅模板
   - 消息中心页                                  - 失败降级为站内消息
   - onShow / 下拉刷新 / 前台轻量轮询
```

**不引入 WebSocket。** 小程序长连接需要处理心跳、断线重连、多进程广播（当前无 Redis），成本远高于收益；企业培训不是秒级协同场景，轮询 + 生命周期刷新足够。

### 2.2 刷新策略（按成本从低到高）

| 层级 | 时机 | 覆盖场景 |
|---|---|---|
| L1 | 页面 `useDidShow` | 切页返回、从考试页回列表（已有） |
| L2 | 下拉刷新 | 用户主动刷新（新增） |
| L3 | App `useDidShow` 拉一次未读数 | 从后台切回小程序（新增） |
| L4 | 关键页面前台 60s 轮询未读数 | 停留在首页/考试列表时（新增，仅一个轻量接口） |
| L5 | 微信订阅消息 | 小程序未打开时（P2，可选） |

L4 只在页面可见时启动，`useDidHide` 清除，避免耗电与无效请求。

## 三、数据设计

### 3.1 新增 `notifications` 表

```sql
CREATE TABLE IF NOT EXISTS notifications (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    tenant_code VARCHAR(64) NOT NULL DEFAULT 'demo',
    recipient_type VARCHAR(20) NOT NULL,          -- employee / user
    recipient_id BIGINT UNSIGNED NOT NULL,        -- employees.id 或 users.id
    type VARCHAR(40) NOT NULL,                    -- 见下表
    title VARCHAR(200) NOT NULL,
    content VARCHAR(500) NOT NULL DEFAULT '',
    link_page VARCHAR(120) NOT NULL DEFAULT '',   -- 小程序页面路径
    link_params VARCHAR(500) NOT NULL DEFAULT '', -- JSON 字符串
    biz_type VARCHAR(30) NOT NULL DEFAULT '',
    biz_id BIGINT UNSIGNED NULL,
    read_at DATETIME NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_notifications_biz (recipient_type, recipient_id, type, biz_type, biz_id),
    KEY idx_notifications_unread (recipient_type, recipient_id, read_at, created_at),
    KEY idx_notifications_tenant (tenant_code, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

- 唯一键保证"同一事件只通知一次"，定时任务重复扫描也不会重复插入。
- `recipient_type='user'` 用于加入审核结果（此时还没有 `employees.id`）。
- 不设外键：通知是日志性质，员工删除后历史仍可保留。

### 3.2 通知类型

| type | 触发点 | recipient | link_page | 受设置开关控制 |
|---|---|---|---|---|
| `exam_assigned` | 考试发布 / 追加指派 | employee | `pages/employee-exams/index` | `notify_assigned` |
| `exam_updated` | 已发布考试修改截止时间 | employee | `pages/employee-exams/index` | `notify_assigned` |
| `exam_closed` | 管理员关闭考试 | 未完成的 employee | `pages/employee-exams/index` | `notify_assigned` |
| `exam_deadline` | 截止前 24 小时，未完成 | employee | `pages/employee-exams/index` | `notify_deadline` |
| `result_ready` | 提交判分完成 | employee | `pages/employee-result/index` | `notify_result` |
| `card_published` | 知识卡发布且关联了考试 | 该考试被指派员工 | `pages/employee-cards/index` | `notify_cards` |
| `join_approved` | 加入申请通过 | user | `pages/employee-login/index` | 始终发送 |
| `join_rejected` | 加入申请驳回 | user | `pages/employee-login/index` | 始终发送 |

> `result_ready` 的意义：员工提交后能立刻看到成绩，但当次通知用于回看入口与"未通过请重考"提醒；对管理员关闭考试后补判的场次同样有效。

### 3.3 可选 `wechat_subscriptions` 表（P2）

```sql
user_id BIGINT UNSIGNED NOT NULL,
template_id VARCHAR(64) NOT NULL,
remaining INT NOT NULL DEFAULT 0,
updated_at DATETIME,
PRIMARY KEY (user_id, template_id)
```

一次性订阅每授权一次 `remaining + 1`，发送成功 `-1`，`remaining = 0` 时跳过并记录日志。

### 5.2 关键实现点

**写入**（`notification_service`）

```python
async def notify_employees(
    tenant_code: str,
    employee_ids: list[int],
    *,
    type: str,
    title: str,
    content: str = "",
    link_page: str = "",
    link_params: dict | None = None,
    biz_type: str = "",
    biz_id: int | None = None,
) -> int:
    """批量写通知，返回实际新增条数（唯一键冲突忽略）。"""
```

- 用 `INSERT ... ON DUPLICATE KEY UPDATE id = id` 实现幂等批量插入。
- 分块 500 条，避免 SQL 过长。
- 通知写入放在业务事务**提交之后**，失败只记日志，不影响发布结果。

**发布考试**（`exam_service.publish_exam`）

```python
assigned = await admin_exam_repository.publish_exam(...)
# 事务已提交
settings = await settings_service.get_settings(tenant_code)
if settings.notify_assigned and assigned > 0:
    employee_ids = await admin_exam_repository.list_assigned_employee_ids(exam_id)
    await notification_service.notify_employees(...)
    logger.info("exam_publish_notified", exam_id=exam_id, count=len(employee_ids))
```

**成绩生成**（`employee_exam_service._finalize_submission`）：判分成功后写一条 `result_ready`，`link_params={"attemptId": attempt_id}`。

**截止提醒**：`main.py` 的 lifespan 里起 `asyncio.create_task`，每 10 分钟执行：

```sql
SELECT e.id, e.title, e.end_at, a.employee_id
FROM exams e JOIN exam_assignments a ON a.exam_id = e.id
WHERE e.status = 'published' AND e.tenant_code = %s
  AND e.end_at BETWEEN NOW() AND DATE_ADD(NOW(), INTERVAL 24 HOUR)
  AND NOT EXISTS (SELECT 1 FROM exam_attempts at
                  WHERE at.exam_id = e.id AND at.employee_id = a.employee_id
                    AND at.status = 'submitted')
```

唯一键 `(recipient, 'exam_deadline', 'exam', exam_id)` 保证每场考试每人只提醒一次。多进程部署时用 `SELECT GET_LOCK('deadline_reminder', 0)` 规避重复扫描。

**员工身份校验**（`core/auth.py`）

给 `get_employee_context` 增加一次轻量校验：

```python
employee = await admin_org_repository.get_employee_context_status(employee_id)
if employee is None or employee["status"] != "active" or employee["tenant_code"] != tenant_code:
    raise AuthenticationError("员工已停用，请联系管理员")
```

用 `SELECT id, status, tenant_code FROM employees WHERE id=%s`（主键）开销可忽略；也可加 30 秒进程内缓存，但停用属于低频高价值事件，建议直接查。

### 5.3 考试列表排序与状态

`list_exams_for_employee` 增加排序权重：

```sql
ORDER BY
  CASE WHEN at_status IS NULL AND e.status = 'published' THEN 0  -- 待完成
       WHEN at_status = 'in_progress' THEN 0
       WHEN at_status = 'submitted' THEN 2
       ELSE 3 END,
  CASE WHEN e.end_at IS NULL THEN 1 ELSE 0 END,
  e.end_at ASC,
  e.id DESC
```

同时在返回模型加入 `computed_state`（`pending / in_progress / done / expired`），前端不再自行拼状态：

- 已发布、未开始、已过 `end_at` → `expired`，显示"已截止"
- 已发布、未开始、未过期 → `pending`
- 有进行中场次 → `in_progress`
- 已提交 → `done`

## 八、微信订阅消息（P2，可选）

### 前置条件

1. 小程序后台申请订阅消息模板（考试指派提醒、成绩通知、截止提醒）。
2. `backend/.env` 增加 `WECHAT_TEMPLATE_EXAM_ASSIGNED` 等模板 ID。
3. 前端在用户主动操作时（如进入考试列表、提交考试）调用 `Taro.requestSubscribeMessage`。

### 限制必须写进产品预期

- **一次性订阅**：用户同意一次只能收到一条，需要反复授权。适合"每次进小程序顺手授权"。
- **长期订阅**：仅对特定类目开放，教育类小程序通常需要申请，且模板字段固定。
- 发送失败（用户拒收、模板过期、额度用尽）必须静默降级为站内消息，不能影响主流程。
- 未绑定微信 / 未授权的员工永远走站内通道。

### 实现要点

```python
class WechatSubscribeService:
    async def send(self, openid: str, template_id: str, data: dict, page: str) -> bool:
        # POST https://api.weixin.qq.com/cgi-bin/message/subscribe/send
        # access_token 进程内缓存 + 提前 5 分钟过期
```

`notification_service.notify_employees` 内部判断：若该员工 `users.openid` 存在且订阅额度 > 0，则发送订阅消息；无论是否成功都写站内通知。

> 建议：先交付站内通道，确认交互闭环后再做订阅消息。订阅消息不会改变数据模型，只是在写入通知后多一个发送动作。

## 十、风险与处理

| 风险 | 处理 |
|---|---|
| 通知表随考试人数线性增长 | 按 `created_at` 保留 180 天，后续加清理任务；单企业规模不大，先不加分区 |
| 60s 轮询增加服务器压力 | summary 接口只查索引，单次 < 5ms；页面隐藏即停；后续可加 `If-None-Match` 或 `unread_count` 版本号 |
| 定时任务多进程重复执行 | `GET_LOCK` + 唯一键双保险 |
| 通知写入失败影响发布 | 通知写入与发布事务解耦，失败只记日志；管理端显示"通知可能延迟" |
| 老考试发布时没有员工绑定微信 | 通知仍写入站内，`notify-preview` 提前暴露未绑定人数 |
| 小程序 tabBar 角标在开发者工具不生效 | 真机验证；失败静默不影响主流程 |
| 微信订阅消息模板审核不通过 | 站内通道独立可用，订阅消息只是增强，不阻塞交付 |

## 十一、验证

### 自动化

- `tests/test_notifications.py`：发布考试生成通知、唯一键幂等、已读/全部已读、未读计数、非本人不可读。
- `tests/test_employee_deadline_reminder.py`：构造 25 小时内截止的考试，断言只生成一次提醒。
- `tests/test_employee_context.py`：停用员工携带旧 token 访问返回 4010。
- `scripts/test_notifications_e2e.py`：
  1. 管理员登录 → 创建考试 → 指派 2 名员工 → 发布；
  2. 员工 A 拉 summary，断言 `unread_count == 1`；
  3. 标记已读，断言归零；
  4. 管理员关闭考试，断言员工 A 收到 `exam_closed`；
  5. 员工 B 提交考试，断言收到 `result_ready`。

### 手工

1. 管理员发布考试，`curl /employee/notifications/summary` 验证。
2. 小程序停留在首页 → 管理员发布 → 等 60 秒 → 角标出现。
3. 小程序切后台再切回 → 角标立即出现。
4. 下拉刷新考试列表 → "新"标签、`已截止` 状态正确。
5. 停用员工 → 旧 token 调接口返回 4010 并跳转登录。
